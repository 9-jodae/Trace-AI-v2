# 문서 참조 그래프 검색 평가

## 목표

Neo4j 참조 검색을 켰을 때 기존 PostgreSQL 벡터·전문 검색보다 정답 문서를 더 잘 찾는지 같은 질문으로 비교합니다. 평가가 끝나기 전까지 팀 서버의 `NEO4J_URI`는 비워 둡니다.

## 범위

1. 본문의 `《문서명》`, `[[문서명]]` 표기를 규칙으로 추출합니다.
2. 문서 제목(파일명 확장자를 제외한 표기 포함)으로 참조 대상을 유일하게 찾을 수 있을 때만 `REFERENCES` 관계를 만듭니다. 본문 첫 줄은 문서 이름 메타데이터로 저장하지 않습니다.
3. Neo4j는 문서 ID, 청크 ID, 문자 위치와 관계만 저장합니다. 본문은 PostgreSQL `accessible_chunks`에서 권한 확인 뒤 읽습니다.
4. 문서 이름으로 찾은 후보는 직접 연결 한 단계까지만 검색하며 `GRAPH_CANDIDATE_LIMIT`으로 개수를 제한합니다.
5. 연쇄 검색은 검색된 상위 문서 3개에서 시작해 본문이 가리키는 방향으로 최대 2단계를 따라갑니다. 단계마다 권한을 확인해 볼 수 없는 문서는 지나가지 않고, 따라간 문서 중 질문과 가까운 청크를 최대 2개만 기존 결과 뒤에 더합니다.
6. 엔티티 추출과 문서 유형 분류는 이 평가 범위에 넣지 않습니다.

## 질문 세트

서버의 시연 문서 18개를 고정하고 관련 질문과 무관 질문을 함께 준비합니다. 질문마다 기대하는 문서 ID를 기록하며, 질문과 문서를 바꾸면 전후 결과를 직접 비교할 수 없습니다.

## 비교 절차

1. 동일한 PostgreSQL, 임베딩 모델, cosine 거리 상한, 질문 및 `RRF` 설정을 사용합니다.
2. 전문 검색 실행 조건을 별도 변수로 기록합니다: 항상 실행 또는 그래프 후보가 5개 미만일 때만 실행. 이는 그래프 시작 문서에도 영향을 주므로 두 결합 방식 비교에서 고정하거나, 별도 실험 축으로 나눕니다.
3. 결합 방식을 비교할 때 동일한 벡터·전문·그래프 후보를 확보한 뒤 (a) 동일 `RRF` 입력에 그래프 결과를 포함하는 방식과 (b) 기존 결과 뒤에 그래프 연쇄 청크를 추가하는 방식을 비교합니다. 후보 생성이나 전문 검색 조건이 달라진 비교는 결합 방식만의 효과로 해석하지 않습니다.
4. 두 방식에서 기대 문서의 `Top-1`, `Recall@5`, `MRR@5`를 계산합니다. `MRR@5`는 정답이 5위 안에 있으면 `1 / 순위`, 없으면 `0`으로 평균 냅니다.
5. 무관 질문에서 그래프가 불필요한 문서를 올리지 않았는지, 접근 불가 문서 ID가 결과에 섞이지 않았는지 확인합니다.
6. 예상보다 나빠진 질문은 데이터 상태, 그래프 seed 매칭, 참조 해석, 전문 검색 실행 여부, `RRF` 순위를 각각 확인합니다.

## 켜기 기준

- 실험군의 `MRR@5`가 기준선보다 높습니다.
- 기대 문서가 검색되지 않던 질문에서 개선되고, 관련 질문의 `Top-1`을 크게 악화시키지 않습니다.
- 무관 질문에 대한 신규 오탐과 권한 범위 밖 문서 노출이 없습니다.
- Neo4j의 실제 Cypher 실행과 빈 그래프·Neo4j 장애 시 벡터·전문 검색 fallback을 확인합니다.

기준을 충족하기 전에는 팀 서버에 `NEO4J_URI`를 설정하지 않습니다. 현재 저장소의 `data/demo_documents.json`은 서버 시연 문서 전체와 다르고 참조 표기도 포함하지 않아, 실제 검색 효과 수치로 사용하지 않습니다. 실제 시연 데이터의 평가가 끝나면 위 표와 함께 결과를 이 문서에 기록합니다.

## 팀 결정 및 추가 확인

### 관계 원본

현재 AI 서버는 문서 본문에 명시된 `《문서명》`, `[[문서명]]`만 `REFERENCES`로 추출합니다. docs199-Server 이슈 #73에서 다루는 manifest의 `document_relations`는 별도 원본이며, AI 서버가 해당 테이블을 읽는 계약은 확인되지 않았습니다. 따라서 검색 그래프와 화면 그래프가 달라질 수 있습니다.

**결정 대기:** manifest와 본문 표기 중 어느 쪽을 관계의 기준으로 삼을지, 용도를 분리한다면 두 결과의 차이를 어디서 검사할지 정해야 합니다. 기준이 확정되기 전에는 양쪽 관계를 임의로 병합하지 않습니다.

### 관계 유형

현재 검색은 명시적 문서 참조 `REFERENCES`만 사용합니다. `CONFLICTS` 관계는 저장·검색하지 않습니다. 충돌 관계의 정의, 근거 위치, 현재 버전·권한을 적용하는 방법이 합의되면 별도 범위로 추가합니다.

### 운영 데이터 점검

- 현재 Neo4j seed 탐색은 문서 노드 제목을 읽어 질문과 대조합니다. 문서가 크게 늘면 제목 인덱스 도입 여부를 실제 데이터 규모와 질의 지연으로 판단합니다.
- 과거 적재 데이터의 사용하지 않는 속성이나 고아 노드는 삭제 전에 대상 건수를 읽기 전용으로 확인합니다. 이번 검색 경로는 제목의 `source`만 seed로 사용하고, 최종 청크는 PostgreSQL 권한 함수에서 다시 확인합니다.
- Neo4j 참조 쓰기 쿼리, PostgreSQL 권한 함수, 실제 문서의 검색 순위는 운영 데이터가 아닌 별도 가상 fixture로 통합 검증한 뒤 결과를 기록합니다.

## 시연 문서 비교 결과 (2026-11-05)

팀원 보고에 따르면 #61 수치는 `travel-policy` 문서 삭제 이후 측정했습니다. 이번 비교에서는 삭제 상태를 유지하고, 해당 문서를 정답으로 기대하던 질문의 gold label에서 제외합니다. 삭제된 문서를 복구해 비교 조건에 넣지 않습니다. 원래 9개 질문의 query별 정답 목록과 hit 상세가 저장소에 없어 집계치만으로 수정된 수치를 확정할 수는 없습니다. 아래 원시 집계는 삭제 문서가 정답에 포함된 상태라면 그대로 비교 지표로 쓰지 않습니다.

시연 문서 18개, 참조 24개, 관리자 범위, 질문 9개(관련 7개, 무관 2개)로 검색 결과만 비교했습니다. 답변 품질은 재지 않았습니다.

| 방식 | 기대 문서 적중 | 기대 밖 문서 |
| --- | ---: | ---: |
| 벡터+전문 | 14/16 | 23개 |

## PR #62 격리 통합 실행 결과

2026-11-05에 `scripts/graph-integration/run.py`를 임시 PostgreSQL·Neo4j에서 실행했습니다. 실제 앱의 `POST /api/v1/agent/chat` 경로와 가상 문서 2개를 사용했고, 임베딩은 결정적 1024차원 테스트 함수, 답변 생성은 테스트 stub입니다. Claude/Bedrock 및 서버 권한 함수는 호출하지 않았습니다. 질문 임베딩 실패 후에도 전문 검색 seed로 관계 검색과 근거 응답이 이어졌고, 벡터 전용·하이브리드 시작점·직접 제목·무관 질문·권한 거부를 포함해 7개 사례가 통과했습니다. 과거 버전 청크는 PostgreSQL hydrate 단계에서 제외됐습니다.

이 결과는 PR #62의 실제 격리 DB 경로 동작 확인이며, #61의 서버 9개 질문 평가와 동일 데이터·질문을 사용한 품질 비교가 아닙니다. 동일 9개 질문 비교는 query별 기대 문서 목록과 18개 시연 데이터의 안전한 평가용 스냅샷이 준비되어야 재현할 수 있습니다. 다음 평가에는 `travel-policy`를 제외한 gold label, 문서 존재/삭제 상태, 현재 버전, 전문 검색 실행 조건(항상/그래프 후보 5개 미만 fallback), 후보 결합 방식(RRF/기존 결과 뒤 추가)을 각각 기록합니다.

코드 비교 시 “RRF와 뒤에 추가”를 상호 배타적인 두 방식으로 보면 안 됩니다. #61도 벡터·그래프(및 조건부 전문 검색) 후보를 RRF로 합친 뒤, 연쇄 청크를 기존 결과 뒤에 추가합니다. PR #62 역시 벡터·그래프·전문 검색 후보를 RRF로 합친 뒤 연쇄 청크를 추가합니다. 주된 차이는 그래프 시작 문서를 #61은 질문의 문서명/Entity로, #62는 PostgreSQL 하이브리드 결과로 정한다는 점과 전문 검색 실행 조건입니다. 결합 전략만의 효과를 보려면 동일 후보를 고정해 별도 실험해야 합니다.
